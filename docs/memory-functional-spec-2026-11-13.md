# Whale Memory 功能规格 v0.1

日期：2026-11-13。状态：需求基线，供后续开发和验收使用。本文描述鲸鱼应表现出的功能，不把设计目标视为已经上线的功能。实现方式见 [memory 架构草案](memory-architecture-v1-2026-11-12.md)，需求讨论记录见 [产品计划](memory-product-plan-2026-11-11.md)。

## 1. 产品目标与范围

鲸鱼是持续相处的私人陪伴角色。Memory 的目的，是让它记住正确的人和事，理解不同情境下的需求，延续共同话题，同时让用户看得到、改得掉。日常聊天应先理解当前话语，再参考适量记忆；记忆不是一份每次都复述的用户档案。

本规格覆盖 owner 私聊与跨设备、QQ 群友及群内公开信息、情绪与相处模式、人物画像、语言特征、记忆管理、来源解释、分享与删除。**当前开发阶段**优先提高 TimlMemBench 中文 dev 的正确率，先解决事实写入和来源追溯这两类短板；长期产品目标仍是兴趣分享和日常聊天的自然接续。Benchmark 分数不能代替陪伴体验验收。

### 核心用语

| 用语 | 含义 |
| --- | --- |
| owner | 鲸鱼的主人；其私有记忆可在本人设备间共用 |
| 事实 | 用户明确表达、可描述为当前状态的信息；与模型推测分开 |
| 情绪事件 | 某一次互动中的情绪、情境和可能需求；不等于长期性格 |
| 相处模式 | 在特定情境下，用户需要什么、什么回应有效的可修正归纳 |
| 人物画像 | 按情境组织的需求、回应和表达偏好，以及低确定度兴趣假设 |
| 来源 | 支撑一条记忆的原话位置、时间、说话人和后续更正关系 |

## 2. 功能要求

### F01 日常聊天与记忆使用

- 回复以当前消息和本会话为先，再取少量相关事实、边界或相处提示。用户刚说的新信息，在后台写入前仍可通过本会话原话参与回答。
- 分享作品、设定、跑团剧情或生活兴趣时，鲸鱼应接住具体内容，提出相关想法或自然追问，不把分享自动解释成求建议。
- 模糊情绪表达如“烦死了”，可以简短问发生了什么；线索不足时不猜过去的具体经历。已经知道情境时，避免重复问同一个问题。
- 相处模式只影响对应情境的回应，不在普通聊天中宣布“我调用了你的画像”。“这次直接给建议”只覆盖当前互动；“以后都这样”才改变长期偏好。
- 普通聊天保持鲸鱼自己的角色卡风格，不模仿用户当下情绪，也不自动使用用户语言画像。首版不为每条消息额外调用一个专门的心理需求分类模型。

**验收场景**：连续聊同一作品时能承接角色或设定；只说“好累”时不翻出一个月前的难过经历；当次明确要求给办法时不继续套用“先安慰”的旧模式。

### F02 自动形成事实记忆

- owner 在普通聊天中明确说出的低风险、具有持续价值的事实，可以在回复发出后自动提取并写入；目标是数秒内可用于后续对话，提取失败不阻塞回复。
- 写入前核对说话人、原话、主体、空间和事实类型。别人的建议、转发文本、短时安排、密码或一次性码不得误记为 owner 的长期事实。
- 同一事实重复出现时合并证据，不生成多条互相竞争的当前事实。模型漏给写入决策或出现含糊冲突时，候选保持待定，不作为确定事实召回。
- 自动写入不在聊天里逐条报备；记忆页应展示新记录、来源，并允许纠错或删除。
- 亲密关系、心理健康倾诉继续走当前云端聊天 API 回复，但默认不自动提取为长期事实。owner 明确说“记住”时，仅写入其指定内容到私有记忆。

**验收场景**：“我最近在准备答辩”可形成有来源的低风险事实；同一句重发只留一个有效事实；“朋友说我应该搬家”不变成 owner 已决定搬家；模型没有分类的候选不会偷偷变成长期记忆。

### F03 更正、撤销与时间状态

- owner 明确更正时，新版本生效，同一事实族的旧版本立即退出普通召回；更正链保留可解释的来源位置。明确撤销许可或要求忘记长期记忆时，相关当前事实立即失效。
- 含糊冲突不自动选择一边当作确定结论。若影响主动提醒，先暂停该提醒；只有冲突影响回答或用户要重新安排提醒时，才自然确认。
- 短期事项应有适用时间或过期状态。历史上曾经写入、现在已失效的事实，在来源解释中仍可被描述为“当时写入，后来更正/撤销”，不能被当作当前事实使用。

**验收场景**：“我以前喝绿茶，现在改喝红茶”只回答当前偏好为红茶；询问为何变化时能指出两次发言与更正顺序；含糊说“最近周五想清静”时不继续执行冲突的周五主动提醒。

### F04 情绪事件与相处模式

- 首版使用文字与用户明确反馈记录 owner 的情绪事件。每次事件分别保存情绪、概括触发、可能需求、来源、鲸鱼的回应及用户反馈；明说和推测必须可区分。
- 普通事件约 90 天后清理。亲密或健康情境只在事件中保存概括类别，例如“亲密关系变化”，不复制人名等细节；已确认的重要共同经历可另行长期保存。
- 两个不同日期或独立情境中的事件，且至少一次有 owner 确认、明确反馈或可归属的后续语气隐式反馈，才可按“需求 + 有效回应”形成长期相处模式。同一段对话重复表达只计一次。
- 隐式反馈始终标记为推测、可撤销。一次明确反对使对应模式停止生效；两次独立的反向隐式反馈使模式暂停并在合适时机确认。
- 群友首版只在当前对话中做短期语气判断，不建立其长期情绪事件档案。

**验收场景**：两次“难过”但一次想被陪伴、一次想要具体办法，不合成同一模式；两次纯模型猜测且没有反馈，不自动形成长期模式；用户纠正情绪判断后，事件与派生模式随之修正。

### F05 每周人物画像与兴趣探索

- 每周回顾近期情绪事件、回应反馈、少量非敏感聊天内容，以及本人分享和讨论的主题，形成按情境区分的“可能需求、有效回应、表达偏好”。本人明确更正或撤销应即时生效，不等待周回顾。
- 宽泛性格判断只能作为可修正的推测，不能单独决定回复。达到 F04 证据门槛的推测性相处偏好可以稳定用于对应情境，但保留推测标记。
- 从讨论推断出的“可能喜好”与本人明确说过的爱好分开，只能偶尔自然试探，不能自动升级为确定事实。转发或引用的内容不能当作本人的语言与兴趣证据。
- 画像项应能逐项查看情境、依据、推测标记和生效状态；用户可直接修改、暂停或删除。

**验收场景**：工作受挫时偏好具体办法、关系受挫时想先被理解，应是两条情境化提示；聊过科幻作品后推测可能喜欢天文，只可偶尔试探。

### F06 语言特征与草稿写作

- 可将同一人自己的私聊与群聊发言汇成统一语言特征，学习用词、句长、语气和表达习惯；不得把别人发言或转发文字混入。
- 高相似度模仿只在该人明确要求“按我的口吻写草稿”时使用。输出是消息或文章草稿，不让鲸鱼在普通聊天里变成该人，也不模仿其当下情绪。
- 群内为适应某位群友而生成的风格提示是另一份数据，只能从该群公开发言提炼，不能读取其私聊画像。

**验收场景**：普通聊天与本人草稿请求使用不同的表达资源；关闭草稿功能后普通聊天风格无变化；不同人的语言特征不会混合。

### F07 主体、空间、分享与群聊

- owner 私有记忆跨本人设备可用，对其他人默认不分享。指定事实可以授权给指定对象并设期限；未指定期限时默认 24 小时，可提前撤回。事实更正后旧版本授权失效，新版本需重新授权。
- 群友可由其本人发言建立个人记忆。某群公开发言形成的群公共事实，只能在同一群内被引用，并说明来自该群本人的发言。心理与关系信息可按此规则回答；住址、门锁、钥匙和访问凭据不得形成可供群内复述的事实。
- 群用风格提示仅在对应群和对应成员生效，不泄露私聊细节。群友说“别记我了”后，停止新写入并删除其个人记忆和群用风格提示。
- 记住一项安排不等于获得主动提醒或执行权限；只有明确授权的事项可主动执行，执行前重新核对授权。

**验收场景**：owner 私聊说的事不会在 QQ 群被其他人问出；群 A 的公开事实不出现在群 B；分享的旧版本更正后不能继续对朋友开放。

### F08 来源解释、记忆页与删除

- 日常回复自然表达，不逐条展示引用。用户追问“你为什么这样记得”时，按其权限展示原话、时间、说话人及更正链；原消息已删除时，不从旧日志重建原话。
- 记忆页应分别展示事实、情绪事件、相处模式和画像，并提供来源与推测标记。用户可以更正、暂停适用项或删除；不要求编辑整段画像文本。
- “忘掉长期记忆”使相关精选记忆、专属证据片段和检索投影不可再召回；“彻底删除记录”还处理原始聊天及派生物。在线删除立即生效，旧离线备份最多保留 30 天，恢复时须重放删除记录。
- 有效事实的必要来源片段随事实保留；更正后的旧原话片段最多再留 30 天，之后只留不含原话的更正链。已删除内容不能因解释请求复活。

**验收场景**：误记的事实在记忆页一键更正后，后续回答只用新版；删除聊天与派生记忆后，普通召回和来源解释都不再出现旧原话。

## 3. 当前开发目标：提高 TimlMemBench dev 正确率

已有完整中文 dev 运行记录为 119/144，但它使用较早的适配器和独立提取，不能直接证明当前产品代码的效果。随后固定同一批官方 dev 的 18 道写入/来源题做诊断；v5 为 9/18，v6 为 11/18，v7 与当前 v9 均为 13/18，v8 和 v10 的试验已撤回。v9 的来源题达到 7/8，但写入题只有 6/10。**当前目标是分别稳定两类题，再回到完整 dev 验证总体结果**；不把局部试跑或混合版本成绩当作完整分数。

### 3.1 面向评测的最小功能链

```text
带说话人与时间的原消息
  → 少量候选提取与逐候选写入决策
  → 统一事实服务：add / preserve / update / revoke / skip / pending
  → 同一事实族的当前版本 + 历史状态 + 来源证据 + 操作记录
  ├─ 当前回答视图：只读有效事实与边界
  ├─ 写入操作视图：按时段说明当时 add/保留/更正/撤销/跳过
  └─ 来源解释视图：按主体和事实族取原始锚点、更正及撤销顺序
```

三种读取视图是功能差异，不要求三套数据库。普通回答不能看到失效事实的旧正文；写入题必须能说明“当时曾写入、如今已撤销”；来源题必须能区分原始发言、更正发言与相邻但无关的发言。跳过决策只需保存原因和来源锚点，写入题需要原话时从仍被允许访问的来源消息读取。适配器只负责把 benchmark 会话映射到产品身份、空间和查询用途，不应凭金标准补写事实，也不应另建一套与产品状态不一致的记忆逻辑。

| 功能切片 | 直接解决的失分 | 产品与适配器的边界 |
| --- | --- | --- |
| 候选决策与临时性 | 临时内容过写、`skip` 漏判 | 提取模型提出候选；产品事实服务保存决策和当前状态 |
| 事实族与更正链 | 旧许可别名残留、历史 `add` 被当现行 | 产品统一版本与失效；适配器提供会话来源 ID |
| 写入操作读取 | 回答把全历史混成当前 Top-5 | 产品提供可查询的时段操作记录；适配器传入官方题目时段 |
| 来源解释读取 | 原始锚点缺失、A/B 说话人错归属 | 产品保留来源关系；适配器仅转换题目中的来源标识 |
| 回答约束 | 有证据仍答“证据不足”、引用无关事实 | 回答器消费有类型的视图；不得用提示词覆盖错误的事实状态 |

### 3.2 评测验收

1. **离线检查**：针对每道失败题记录候选、写入决策、当前事实、历史操作、提供给回答器的证据和最终答案；先定位错误发生在哪一步。负向测试覆盖旧事实不可普通召回、待定候选不可召回、来源不能错归说话人。
2. **同批 18 题**：固定 10 道写入题和 8 道来源题，逐题报告。现有运行只冻结事实候选，治理操作仍由模型重采样；下一步须冻结治理输出及可重放的目标映射，再做同条件配对比较。两类题都要分别报告，不以一类上涨掩盖另一类下降。
3. **完整 dev**：诊断切片稳定改善后，重跑官方中文 dev 全部题型，报告总分、题型分数、模型调用与费用。与早期 119/144 只能作历史对照；要判断代码因果收益，应在同一冻结输入和裁判条件下运行旧版与新版配对对照。
4. **产品一致性**：对同一事实的普通回答、写入审计和来源解释必须从同一产品状态得出一致结论。Benchmark 适配器通过不代表 QQ/Studio 真实入口已验收。

这阶段暂不为冲分开发情绪模式、周度画像、语言模仿或大型图/向量存储；它们仍是 F04–F06 的产品需求，待事实与来源链稳定后继续交付。

## 4. 产品功能交付顺序

下表描述完成当前 dev 提分阶段后，面向真实陪伴体验的交付重点。

| 顺序 | 可体验结果 | 完成判据 |
| --- | --- | --- |
| 1 | 日常聊天能自然接续兴趣话题，当前话语优先于旧模式 | 固定对话场景人工盲评；无明显翻旧账或机械追问 |
| 2 | 低风险事实自动形成，明确更正和撤销立即生效 | 本地端到端测试 + TimlMemBench 事实/来源诊断题；区分产品缺陷与适配器缺陷 |
| 3 | owner 情绪事件和情境化相处模式参与回应 | 两次独立事件、反馈、纠错、过期和自然度场景通过 |
| 4 | 记忆页可检查、修正和暂停画像 | 用户从界面完成一次误记纠正与画像暂停 |
| 5 | 群场景、指定分享、语言草稿和彻底删除形成闭环 | 跨人/跨群、分享更正、草稿开关与删除恢复场景通过 |

此顺序表示体验验收的重心，不表示前序实现完全阻塞后序功能。每项都应在真实入口验证；只有单元测试或 benchmark 分数不代表已交付。

## 5. 当前实现与差距（2026-11-13）

已有代码包括事实服务及版本状态、按来源读取产品写入决策的首版操作视图、部分自动提取与后台任务、轻量回应上下文、owner 情绪事件与反馈、画像存储及周回顾代码、部分记忆页入口，以及 TimlMemBench 适配与回归测试。这些说明已有开发基础，**不表示 F01–F08 已整体验收**。当前明确差距如下：

1. TimlMemBench 同一批 18 道事实/来源题的当前 v9 完整重跑为 13/18，相比 v5 的 9/18 净增 4 题；来源 7/8、写入 6/10。随后 v10 的 12/18 已撤回。完整 dev 尚未用当前版重跑。该结果不能代表全部 memory 能力，也不能证明产品聊天自然度。
2. 当前自动提取和周回顾虽已有代码，仍需按 F02/F05 逐项验证真实聊天、重试、长期稳定性与记忆页操作；不能把“有接口”视为体验闭环。
3. 逐事实版本分享、群公共事实的完整读取、统一语言特征的草稿路径、两种删除及备份恢复尚未完成产品验收。
4. 自然度、情绪适配、兴趣讨论和跑团群实际对话需要独立场景集及人工评审，不能用事实问答 benchmark 代替。

## 6. 需求变更原则

本文件是当前已确认的产品行为基线。后续讨论若修改某项功能，应同时更新对应 F 编号、验收场景和架构草案；代码进度单独记录，不反向改写需求。尤其要区分“用户明确说过”“系统推测”“已经实现”“已经在真实入口验收”四种状态。
